# M17 — Extração: núcleo concreto e ganchos para design systems

**Visão do dono:** pptsx é a base, como o React é a base de MUI, Chakra e dos DS internos de cada empresa. O núcleo faz render; design systems nascem em cima, em libs separadas, **sem hackear nada**. Hoje a linha está borrada: `examples/` carrega componentes, layouts, tokens e tema que o guia apresenta como "prontos", e faltam quatro ganchos que um DS precisaria contornar (identidade de componente, regras de lint próprias, render isolado para catálogo e extensão do MCP).

**Execução:** sequencial, uma etapa por vez; `typecheck` limpo, `npm test` verde, um commit `feat(m17-N): …` por etapa; notas em `docs/work/reports/M17.md`. Regras do `CLAUDE.md` valem. Este marco **não adiciona recurso de slide**: adiciona superfícies de extensão e tira do núcleo o que é opinião de marca.

**Pronto quando:** o repositório é um monorepo com `pptsx` (núcleo), `@pptsx/ds-kit` e `@pptsx/ds-base`; o núcleo não exporta nenhum componente além das primitivas e não contém tokens, tema pronto nem layout de marca; `ds-base` reconstrói a demo, a galeria e os decks de `texto/`, `dados/` e `diagrams/` **usando só a API pública** de `pptsx` e do `ds-kit` (nenhum import de `pptsx/src/...`), com frames idênticos às fixtures (±1 pt); um DS de terceiro de exemplo (`examples/third-party-ds/`, 3 componentes, 1 tema, 2 regras de lint) é criado do zero pelo agente virgem só com o guia do `ds-kit` em ≤ 2 builds; as regras do DS aparecem no `pptsx lint` e no MCP sem o núcleo citar o DS.

## A linha, por escrito

| Fica no núcleo (`pptsx`) | Vai para `@pptsx/ds-kit` | Vai para `@pptsx/ds-base` (e para cada DS) |
|---|---|---|
| primitivas e tipos CSS; resolve/layout/fit/emit/preview; diagnósticos e schema; breakpoints, `ctx.pick`, paginação; `defineLayout` (vira master); **contratos** `Theme`/`DocumentProperties`; CLI, `lint` com regras da engine, `preview --serve`, MCP; `defineComponent` e `defineDeck` | `defineTokens`, `themeOf`, `createVariants`, `slots`, `defineRule` (lint), `catalog` (render de componente isolado + fixtures), `defineDs` (empacota tudo: componentes, tema, regras, guia, schema), multimarca, testes de contrato de componente | tokens, tema, layouts (`Cover`, `Content`, `Closing`…), componentes (`Bullets`, `KpiCard`, `KpiRow`, `TwoColumn`, `Timeline`, `Tag`…), regras de marca, guia do DS, galeria |

Regra para o futuro: **se uma funcionalidade só faz sentido com uma marca, não entra no núcleo.** Se o núcleo precisa saber o nome de um componente para funcionar, é um gancho faltando.

## Decisões de desenho

1. **`defineComponent` no núcleo é mínimo e sem opinião.** Dá identidade (nome no path mesmo com HOC/anônimo), `defaultProps`, metadados livres (`meta`) que o lint e o catálogo leem, e nada de variantes/slots/estilo: isso é `ds-kit`. Componente comum (função solta) continua funcionando como hoje.
2. **Lint tem API de regra pública e estável**: uma regra é função pura sobre a árvore resolvida (com `css`, `path`, `meta` do componente, `ctx` do tamanho e o `Theme` se houver) que devolve achados no mesmo `LintFinding` do núcleo. O núcleo descobre regras por `pptsx.config.ts` (`lint: { rules: [...] }`) e pelo `defineDs`; nunca por nome de pacote.
3. **Catálogo é uma função do núcleo** (`renderFragment`) e um comando do `ds-kit` (`catalog`). O núcleo só sabe renderizar "um elemento num slide de tal tamanho"; o `ds-kit` sabe iterar variantes, montar o overview e gravar fixtures.
4. **MCP agrega**: `guide` e `schema` do núcleo passam a receber **fontes** (o DS registra o seu guia e o seu schema de props pelo `defineDs`); `build`/`diagnose`/`preview` não mudam.
5. **Tema continua um contrato do núcleo** (é recurso do arquivo PPTX); `ds-kit` fornece `themeOf(tokens)` e validações; `ds-base` fornece um tema.
6. **Exemplos do núcleo usam só primitivas.** `examples/` do núcleo fica com `hello`, `layout-test`, `overflow`, `calibration*`, `probe/*` e os decks de `docs/readme/decks/` reescritos sem componentes; tudo que tem marca (demo, galeria, showcase, `texto/`, `dados/`, `diagrams/arquitetura`) migra para `ds-base/examples/`. Os testes de paridade do núcleo continuam sobre **cópias congeladas** (`tests/examples/legacy/`, já existe) e sobre decks só de primitivas; `ds-base` ganha os seus.
7. **Monorepo com npm workspaces**, publicação independente, versionamento por pacote; `pptsx` segue para 1.0 quando os aliases saírem; `ds-kit` e `ds-base` começam em 0.1.0.

## Etapas

### M17-1 — Ganchos no núcleo (contrato)
- `src/core/types.ts`: `ComponentMeta` (`{ readonly name: string; readonly displayName?: string; readonly ds?: string; readonly tags?: readonly string[]; readonly [key: string]: unknown }`); `Component<P>` ganha a propriedade opcional `[COMPONENT_META]` (símbolo, como `PRIMITIVE_KIND`); `ResolvedBase` ganha `component?: ComponentMeta` (o componente mais externo que gerou o nó, o mesmo que dá o segmento do path).
- `defineComponent(meta | name, fn, defaults?)` em `src/primitives/` e exportado; `expand.ts` usa `displayName ?? name` no path e carrega `meta` para o nó.
- `LintRule` público em `src/lint/rule.ts`: `{ readonly id: string; readonly severity: 'error' | 'warning' | 'info'; readonly check: (node: ResolvedNode | ResolvedSlide, ctx: LintContext) => readonly LintFinding[] }`; `LintContext = { size: DeckContext; theme?: Theme; slide: number; path; component?: ComponentMeta; parent? }`; `lintDeck` aceita `rules` externas e as roda depois das internas; `PptsxConfig.lint?: { rules?: readonly LintRule[]; disable?: readonly LintCode[] }`.
- `renderFragment(element: SlideElement, options: { size: SizeSpec; padding?: number; fonts?; theme? })` em `src/render.ts`: embrulha o elemento num `Slide` e devolve `{ positioned, diagnostics, svg, png? }` sem gravar nada.
- MCP: `McpContext` ganha `guides: readonly { id, text }[]` e `schemas: readonly { id, schema }[]`; `guide({ source?, section? })`, `schema({ source?, primitive? })`; descoberta pelo `pptsx.config.ts` (`ds: [defineDs(...)]`) e por `--ds <pacote>`.
- `DsManifest` (contrato do que um DS entrega): `{ name, version, components: ComponentMeta[], theme?: Theme, rules: LintRule[], guide?: string, schema?: object, examples?: string[] }` e `defineDs(manifest)` **no núcleo** (é só identidade; o kit preenche).
- CONTRACTS §M17. Testes: path com `displayName`; `component` no nó; regra externa roda e aparece no `--json`; `renderFragment` de um `Box` dá frames e SVG; MCP agrega um guia de teste.
- **Pronto quando:** tudo acima compila, testado, e nenhuma fixture muda.

### M17-2 — Workspaces e `@pptsx/ds-kit`
- `package.json` raiz com `workspaces: ['packages/*']`; `packages/pptsx` (o núcleo atual movido, `files`/`exports`/`bin` intactos; `npm run test:package` continua), `packages/ds-kit`, `packages/ds-base`. Scripts raiz orquestram (`npm test -ws`). CI atualizada.
- `@pptsx/ds-kit` (depende de `pptsx` como peer):
  - `defineTokens(t)`: tipado, congela, valida cores/fontes, expõe `tokens` e `scale(name, factor)`;
  - `themeOf(tokens, map)`: mapeia tokens para `Theme` (accent1..6, dark/light, fontes) com validação de contraste mínimo (WCAG AA como aviso);
  - `createVariants<P>({ base, variants, defaults })`: resolve variantes em props CSS, respeitando responsivo (`size={{ base: 'md', tall: 'lg' }}` funciona porque usa `mapResponsive`);
  - `slots`: convenção tipada para componentes com áreas nomeadas (`header`, `body`, `aside`) com `Child` por slot;
  - `defineRule(id, severity, check)` e regras prontas opcionais: `colors-from-tokens`, `fonts-from-theme`, `no-inline-style`, `max-children(component, n)`, `only-on-slide(component, index)`;
  - `catalog({ ds, sizes, out })`: para cada componente com `meta.catalog` (lista de casos `{ name, props }`), chama `renderFragment` em cada tamanho, grava PNGs, um overview por componente e `fixtures/<component>.json` com frames; `catalog --check` compara com as fixtures (±1 pt) e falha em CI;
  - `defineDs` do núcleo re-exportado com helpers para montar `guide` (concatena os `.md` dos componentes) e `schema` (dos tipos de props via o mesmo gerador do MCP).
- Testes do kit: variantes responsivas, `themeOf` com contraste, catálogo gera fixtures e `--check` detecta 2 pt de diferença, regra `colors-from-tokens` acusa hex solto.
- **Pronto quando:** `npm i` na raiz instala tudo, `npm test` roda os três pacotes, e um componente de teste do kit passa pelo catálogo.

### M17-3 — `@pptsx/ds-base` extraído
- Move `examples/tokens.ts`, `theme.ts`, `layouts/`, `components/`, `gallery/`, `demo.tsx`, `showcase.tsx`, `long-list.tsx`, `charts.tsx`, `texto/`, `dados/`, `diagrams/arquitetura.tsx` para `packages/ds-base/{src,examples}` e os reescreve com `defineComponent`, `createVariants`, `slots` e `defineTokens`/`themeOf`; cada componente ganha `meta.catalog` e um `.md` curto (uso, props, armadilhas) que vira o guia do DS.
- Regras de marca do `ds-base`: `colors-from-tokens`, `fonts-from-theme`, `kpi-row-max-4`, `cover-only-first`.
- `defineDs({ name: '@pptsx/ds-base', … })` exportado; `pptsx.config.ts` dos exemplos do `ds-base` registra o DS.
- Paridade: fixtures `css-positioned.json` e as do M12–M14 migram para `ds-base/tests` e têm que bater (±1 pt); os testes de paridade do núcleo passam a usar só `tests/examples/legacy/` e decks de primitivas.
- **Pronto quando:** `ds-base` reconstrói todos os decks migrados com os mesmos frames, o catálogo gera overview de cada componente e `pptsx lint` com o DS registrado acusa um hex fora dos tokens.

## Fora deste marco
Tema runtime (trocar tokens dentro de um deck); componentes com estado; marketplace de DS; migração automática de decks para componentes do DS (o `lint --fix` continua só para aliases).

## Riscos
- **Mover arquivos quebra imports de scripts e docs**: fazer a movimentação com `git mv` e um passo de busca por caminhos antigos antes de cada commit.
- **Paridade durante a extração**: só aceitar diferença de fixture se for explicada por `defineComponent` mudando um path (e nesse caso atualizar o path, não o frame).
- **`renderFragment` e paginação**: um fragmento não pagina; o catálogo documenta que `paginate` só é testado em deck completo.
